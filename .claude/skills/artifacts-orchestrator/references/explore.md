# Phase 0b: explore

Read when Phase 0b starts (a new artifact skill, after triage). The entry and exit conditions are in `SKILL.md`.

A new artifact skill that is not derived is not specified from a description alone (a skill derived from an adopted anchor skips this phase, see `SKILL.md`): the person first sees what an unassisted session produces for one complex prompt, three times over, and picks the reference. The requirements are the `skill-exploration` capability in `openspec/specs/`, or, while the change is in flight, its spec delta.

1. **Brief.** Ask the person for the brief of the skill: the artifact type, who it is for, the sources it starts from, optionally a concrete use case. Do nothing until it names at least the artifact type and the sources; ask for what is missing.
2. **Issue.** File the work item as in Phase 0 step 1, with the brief as the issue body.
3. **Case.** Write one case, `complex/`, under `_agents_workspace/explore-<slug>/cases/`, in the testbed layout (`prompt.md` with `name: sketch-complex`, `runs: 3`, `max_turns`, `timeout_seconds` and `allowed_tools` without `Skill`; `graders/file.md`, a `file_exists` grader on the deliverable). The prompt covers the advanced and complex cases typical of the artifact type: every feature the brief implies, from a structured source where the brief names one. Read the "Fair cases" section of `.claude/skills/skill-eval/SKILL.md` before writing it, and follow it: the prompt names one self-contained HTML page and its file name, asks for features as a user would, and never mentions the plugin, a skill or the plugin's design. Use the brief's use case where it has one.
4. **Sketch.** Run `evals/sketch.sh _agents_workspace/explore-<slug>/cases`, with no cost confirmation. It runs the prompt three times in isolated, skill-free sessions, keeps the deliverables under `evals/results/sketch-<run-id>/` and prints the sketch report; its header gives the defaults and options.
5. **Present.** Open the three deliverables in a browser. Give the person the report (cost included, and the prompt fingerprint the three runs share) and your own short inventory in two lists: the features present in all three runs (what the unassisted model does constantly), and the features present in only some, naming which run has each (the variability of the unassisted model); functionality and richness first. Ask one question: which run is closest to the functionality and richness wanted, or whether none fits, and any hints. Never recommend a run: the choice is the person's.
6. **Record.** Comment on the issue with the chosen run (or that none fits), the two feature lists of step 5 with the runs that have each feature (so the record stands without the ignored files), and the hints. Paths are relative to the repository (`evals/results/sketch-<run-id>/...`), never absolute; no user name and no transcript. The sandbox gives each session the account's e-mail address, so check that a sketch does not echo it (or any other personal detail) before you quote from it; the sketches themselves are never committed or published.
7. **Hand on.** Invoke `openspec-propose` (Phase 0 step 2) with the brief, the complex prompt, the chosen run's deliverable path, the hints and the issue number. The rules for the proposal's Exploration section and for seeding the testbed from the complex prompt are in `openspec/config.yaml`, which that workflow applies.
