# Test scenarios

Read when checking or changing the orchestrator's workflow, not during a run.

- **Normal.** "Add a WBS skill." After Phase 0b, `openspec-propose` writes the change and the user approves it → brief → the builder implements and ticks the tasks → the reviewer renders two artifact types in two themes and both modes, verdict `pass` → summary → on go-ahead: commit, archive, issue commented and closed.
- **Explore.** "Add a WBS skill." The brief names the artifact type and its sources → the issue is filed with it → `evals/sketch.sh` returns three skill-free deliverables of the one complex case → the person sees them with the inventory of what is constant and what varies, chooses the second run with a hint, nothing is recommended → the issue is commented → `openspec-propose` writes a proposal with an Exploration section. "Add a field to the ERD skill" skips this phase.
- **Derived.** "Add an object diagram skill, derived from the class diagram" (issue and anchor named) → triage skips Phase 0b → `openspec-propose` writes a proposal with a Derivation section (anchor, what is reused, each added shape mapped to a role or named as a missing role, the sample case, what is left out) and the user approves it → the builder writes the sample model under `evals/<skill>/sample/` → visual review and skill review pass → Phase 3c renders the sample with `default` and `alt`, the user opens both and accepts → the validation entry (`Decision: adopt (validated, not measured; derived from uml-class-diagram) (<date>)`) is appended to `RESULTS.md` → Phase 4 runs `python3 evals/kpi.py doc` (the README row reads "not measured", derived from the anchor) → archive. Had the user asked for changes, the builder gets the notes (two fix rounds at most); had the build needed a new layout engine, the change goes back to the spec process and the skill takes Phase 0b as an anchor.
- **Fix loop.** The reviewer reports `VC-1 fail` for a literal color in a template → the builder moves the value to a token role in the shared source → the second review re-checks every invariant and passes.
- **Evaluation.** The reviewer says `pass` on a new skill → Phase 3b runs the testbed, the report says `below target` with time unmet → the user compares the deliverables, records `adopt` with a reason in `RESULTS.md` → Phase 4. Had the user recorded `rework`, the builder gets the report and the notes, then review and evaluation repeat. "Add a detail level to the ERD skill" passes its visual and skill reviews and goes to Phase 4 with no evaluation, unless its proposal declares a major refactoring or the user asks for one.
- **Skill review.** A change to the ERD renderer and its `SKILL.md` passes the visual review → Phase 3a dispatches the skill reviewer on `skills/erd/` → it moves a rule repeated in `SKILL.md` and `references/model.md` to the reference, adds when to read it, runs nothing, writes `03a_skill_review.md` → structural tests and validation pass → Phase 3b evaluates the reviewed skill. A change to a theme alone has no Phase 3a.
- **Error.** No renderer is available for the artifact's medium → verdict `incomplete` with VC-5 and VC-6 `not verified` → the user is told which tool is missing and decides; nothing is archived as passing by default.
- **Trivial.** "What does the visual contract say about dark mode?" → answered directly from `visual-contract`; no agents, no workspace.
