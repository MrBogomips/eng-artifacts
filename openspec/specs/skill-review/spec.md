# skill-review Specification

## Purpose
Settles how the text of a skill is reviewed before the skill is evaluated: every skill a change adds or changes is reviewed with the skill-creator skill, with the focus on how the skill describes its context management, and the review applies its improvements without running any test or evaluation.

## Requirements

### Requirement: Skills touched by a change are reviewed
Every change that adds or changes a skill's `SKILL.md`, of a plugin skill or of a harness skill, SHALL have each such skill reviewed once its build is done. Skills generated by a tool and never edited by hand (the OpenSpec skills) SHALL NOT be reviewed. A change that adds or changes no skill SHALL have no skill review.

#### Scenario: Plugin skill changed
- **WHEN** a change modifies the `SKILL.md` of the ERD skill
- **THEN** the ERD skill is reviewed before the change is evaluated

#### Scenario: Harness skill changed
- **WHEN** a change modifies the orchestrator's `SKILL.md`
- **THEN** the orchestrator skill is reviewed

#### Scenario: No skill touched
- **WHEN** a change modifies only a renderer and a theme
- **THEN** no skill review runs

#### Scenario: Generated skill
- **WHEN** an OpenSpec update regenerates the OpenSpec skills
- **THEN** they are not reviewed

### Requirement: Review precedes the evaluation
The skill review SHALL run after the visual review passes, or straight after the build when the change has nothing visual, and before the skill's evaluation, so the evaluation measures the reviewed text.

#### Scenario: Skill change with a visual part
- **WHEN** a change to an artifact skill passes its visual review
- **THEN** the skill review runs next, and the evaluation runs on the skill as the review left it

#### Scenario: Harness change
- **WHEN** a change to a harness skill has nothing to render
- **THEN** the skill review runs straight after the build

### Requirement: Focus on context management
The review SHALL be done with the skill-creator skill and SHALL look at how the skill describes its context management: what loads when the skill triggers and what only on demand, the length of `SKILL.md`, a stated moment to read each reference, deterministic work left to the skill's scripts rather than spelled out in prose, no content repeated between `SKILL.md` and its references, and the frontmatter description as a trigger.

#### Scenario: Reference read without a stated moment
- **WHEN** a `SKILL.md` lists a reference without saying when to read it
- **THEN** the review adds the moment, or records why it leaves the reference as it is

#### Scenario: Content repeated
- **WHEN** a rule appears both in `SKILL.md` and in one of its references
- **THEN** the review keeps it in one place and points to it from the other

### Requirement: Pure review, no tests or evaluations
The skill review SHALL NOT run tests, evaluations, agent sessions or a description-optimization loop. It SHALL apply its improvements directly to the reviewed skill's `SKILL.md` and `references/` files and to no other file.

#### Scenario: Review with skill-creator
- **WHEN** the skill review runs
- **THEN** no evaluation, test run or agent session is started by it, and only the reviewed skill's `SKILL.md` and references may differ afterwards

### Requirement: Behavior set by the specs is kept
The skill review SHALL NOT change behavior that the change's specs or the current specs set. When an improvement would need such a change, the review SHALL leave the text as it is and report the conflict, which goes back to the spec process.

#### Scenario: Improvement conflicts with a spec
- **WHEN** the review finds that a step the spec requires could be dropped to save context
- **THEN** the step stays, and the report names the conflict for the spec process

### Requirement: Independent reviewer and report
The review SHALL be done by an agent that starts from the skill, the change and its specs, not from the builder's account of the work. It SHALL write a report that lists each edit with its reason and what it deliberately left alone. After the review, the structural tests and the change's validation SHALL run again and pass.

#### Scenario: Report written
- **WHEN** the review of a skill ends
- **THEN** a report in the change's workspace lists each edit with its reason and each point left alone, and the structural tests and the change's validation pass

### Requirement: Unavailable reviewer is reported
When the skill-creator skill is not available in the session, the skill review SHALL be reported as skipped in the change's summary and SHALL NOT be silently omitted.

#### Scenario: skill-creator missing
- **WHEN** a change touches a skill and the session has no skill-creator skill
- **THEN** the change's summary says the skill review was skipped and why
